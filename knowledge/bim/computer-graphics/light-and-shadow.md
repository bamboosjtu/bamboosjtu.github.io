# 有光为什么还要阴影：从可见性到 Shadow Map

创建了灯光，物体已经有明暗，为什么还要单独开启阴影？`shadow` 为什么挂在 `light` 上？一块贴了灰色透明图片的平面，为什么也被称为阴影？

先分开两个问题：**表面如何对光作出响应，以及光能不能到达这个表面。** 常见实时渲染会用不同的计算去近似处理它们。

## 一、光照计算不自动知道沿途有没有遮挡

把球放在平面上，再从侧上方放一盏灯。仅靠局部光照模型，可以根据球面朝向、光的方向、材质与观察方向计算明暗。但这还没有回答：从平面上的某一点连向光源，中间是否被球挡住？

这就是阴影要补充的可见性信息。它不是用来修复材质颜色，而是决定某盏灯的直接照明是否能到达该处。

用简化的表达理解：

`某盏灯的直接照明贡献 = 可见性 × 入射光与表面反射的计算结果`

这里的可见性可以先理解成“能照到”或“被挡住”。真实的面光源、柔和阴影以及各种实时过滤算法会使情况更复杂。处在阴影里的点也不一定全黑，因为它还可能接收到其他灯光、环境照明或间接光。

## 二、Shadow Map 是从灯的位置重新看一次场景

以方向光的基本阴影映射为例，分两步理解。

### 第一步：从光源看，记录最近的表面

渲染器使用光源对应的阴影相机，将参与投影阴影的几何绘制到一张离屏纹理中，记录深度信息。这张图回答的是：光向这个方向前进，最先遇到的表面在哪里？

它不是普通颜色照片，也不是把黑色影子从物体上“剥”下来。

### 第二步：从正常相机看，查询这个点是否被挡住

绘制用户看到的画面时，把待着色的表面位置转换到光源的阴影坐标中，取出对应的深度并比较。

- 如果这个点比光源看到的最近表面更靠后，说明光到达它之前碰到了别的表面。
- 如果它就在最近表面附近，则通常认为这盏灯可以照到它。

实际实现还要处理深度精度、偏移与过滤。这是近似方法，所以会出现锯齿、自遮挡条纹和阴影脱离物体等问题。

## 三、为什么 shadow 属于 light

因为“挡住没有”是相对于某个光源提出的问题。

同一个球面对左边的灯可能无遮挡，面对右边的灯却被另一个物体遮住。每盏灯需要自己的观察方式、深度记录与参数，因此 Three.js 把相应配置组织为 `light.shadow`。

对常见 WebGL 阴影实现：

- 方向光用正交阴影相机，表达平行光方向上的遮挡。
- 聚光灯用透视阴影相机，表达光锥内的遮挡。
- 点光源需要覆盖多个方向，通常需要六个方向的视图，成本更高。

`AmbientLight` 没有一个明确的照射方向，不能像方向光那样定义一张普通投影阴影图。不要把“都是 Light 的子类”理解成它们具有相同的阴影能力。

## 四、四个开关各自负责什么

下面是已有场景时的配置片段，假设 `light` 为支持阴影的方向光，球和平面使用可接收光照阴影的材质：

```js
renderer.shadowMap.enabled = true;
light.castShadow = true;
sphere.castShadow = true;
plane.receiveShadow = true;

light.shadow.mapSize.set(1024, 1024);
light.shadow.camera.left = -5;
light.shadow.camera.right = 5;
light.shadow.camera.top = 5;
light.shadow.camera.bottom = -5;
light.shadow.camera.near = 0.5;
light.shadow.camera.far = 30;
light.shadow.camera.updateProjectionMatrix();
```

- `renderer.shadowMap.enabled`：是否启用这套阴影机制。
- `light.castShadow`：是否为这盏灯计算阴影。
- `mesh.castShadow`：这个物体是否参与投影阴影的计算。
- `mesh.receiveShadow`：正常绘制这个物体时，是否应用接收到的阴影。

物体可以同时投射和接收阴影。上面的数值只是小场景示例，光的位置、朝向、阴影相机范围与场景尺度必须相互匹配。

没有看到阴影时，先依次检查：灯是否支持；开关是否开启；材质是否支持；遮挡物和接收面是否位于阴影相机覆盖范围；光源朝向是否正确。不要一开始就把贴图尺寸拉满。

## 五、Geometry 没有“变成”Shadow

实时阴影过程中，Geometry 仍然是几何数据。渲染器只是把它用于另一次深度或距离相关的绘制，得到阴影查询所需的数据。

`LightShadow` 是阴影配置与相关资源的组织，不是 Scene 里的一个黑色 Mesh。最终的暗部通常是在接收表面着色时算出来的，不是另一件独立黑色物体贴在上面。

而教程里把一张柔边黑影放到平面上，是另一种方法：在场景里直接添加一个看起来像阴影的 Mesh。两者要分开理解。

## 六、实时阴影、烘焙与假阴影

| 方法 | 信息从哪里来 | 灯或物体移动后怎样 |
|---|---|---|
| 实时 Shadow Map | 运行时从光源视角计算遮挡 | 重新计算后可以跟随变化 |
| 烘焙光照 / 阴影 | 预先计算并存入纹理等数据 | 静态结果通常需要重新烘焙 |
| 透明平面假阴影 | 人工画出的或程序生成的暗色图案 | 需要自行更新位置、大小与形状 |

“用 PlaneGeometry 加 alphaMap”只能说明显示方法，不能单凭这段代码判断它是不是烘焙。图片若来自预先计算的场景照明，可以承载烘焙结果；若只是画一个渐变圆，就是廉价的接触感提示。

下面的片段演示**人工假阴影**。假设 `shadowMask` 是已经加载的灰度纹理，白色代表需要显示黑色阴影，黑色代表透明：

```js
const shadowMaterial = new THREE.MeshBasicMaterial({
  color: 0x000000,
  alphaMap: shadowMask,
  transparent: true,
  opacity: 0.35,
  depthWrite: false
});
const fakeShadow = new THREE.Mesh(
  new THREE.PlaneGeometry(2, 2),
  shadowMaterial
);
fakeShadow.rotation.x = -Math.PI / 2;
fakeShadow.position.y = 0.01;
scene.add(fakeShadow);
```

`alphaMap` 是材质的属性，不是 Mesh 的属性。平面只是承载图案的几何体。略微抬高是为了减少与地面的深度冲突，但并不能保证所有视角和场景尺度都合适。

这种图案可以独立存在、脱离灯光；这也意味着它没有真实的遮挡推导。抬高球、移动灯光或把地面改成曲面，它就可能露出破绽。

## 七、阴影清晰度为什么不只取决于 mapSize

阴影贴图有固定的纹素数量。如果方向光的阴影相机覆盖范围非常大，每个纹素就要代表很大一片世界空间，小物体的细节自然难以表示。

优先顺序通常是：

1. 让阴影相机覆盖需要的区域，别浪费分辨率。
2. 在性能允许范围内增加贴图尺寸。
3. 小幅调整 `bias` 或 `normalBias`，减少错误自遮挡，同时检查阴影是否脱离或变形。
4. 再选择合适的过滤方式与更新策略。

`DirectionalLightHelper`、`SpotLightHelper` 等灯光辅助对象主要帮助观察对应灯光的位置、方向等；`CameraHelper(light.shadow.camera)` 更直接地显示阴影相机的覆盖范围。它们是调试可视化工具，不会改善照明本身。

## 八、不要把环境光近似等同于全局光照

漫反射和镜面反射描述表面如何反射光；直接与间接描述光到达表面的路径。这两组分类不在同一层。

- **直接照明**：光源直接照到表面。
- **间接照明**：光先经过其他表面反射，再到达这里。
- **全局光照**：考虑场景内光的传播与表面间相互影响，而不只在单点套一个局部明暗公式。

传统着色模型中的常量环境项，或简单的环境灯，只是对部分照明效果的粗略补偿。它不会自动算出墙面反射来的有色光。Shadow Map 主要补充直接光的遮挡，也不会自动带来完整的间接照明。

## 九、用一个球验证四件事

1. 关阴影、保留灯光：球仍有明暗，但平面可能没有投影阴影。
2. 开阴影：平面的暗部出现，说明局部光照与光源可见性是两回事。
3. 移动灯光：实时阴影变化，人工假阴影不会自动知道发生了什么。
4. 放大阴影相机范围、保持 mapSize：观察细节变差，理解纹素分辨率与世界覆盖范围的关系。

理解到这里，`light.shadow` 就不再是一个需要死记的接口：它是在管理这盏灯“从哪里看、看多大范围、用多少精度记录遮挡”。
