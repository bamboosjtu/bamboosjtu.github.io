# BIM 学习地图

BIM 的核心不是“把工程画成立体的”，而是让工程对象及其信息在全生命周期内可定义、可交换、可检查、可协同、可追溯、可持续使用。

## 一、BIM 核心价值

BIM 通常写作 **Building Information Modeling**。如果只按字面翻译，很容易把注意力放在 “Model” 上。但从工程实践看，更值得关注的是中间那个词：**Information**。BIM 对象通常至少包含以下几类内容：

| 层次 | 回答的问题 | 示例 |
|---|---|---|
| 几何 Geometry | 长什么样 | 主变压器外形、尺寸 |
| 空间 Spatial | 在哪里 | 位于某 500kV 变电站、某设备区 |
| 语义 Semantic | 是什么 | 主变压器、套管、断路器 |
| 属性 Property | 有什么参数 | 额定容量、额定电压、制造厂商 |
| 关系 Relationship | 与谁有关 | 属于某系统、连接某设备、位于某空间 |
| 状态 State | 现在处于什么阶段 | 设计、施工、验收、投运 |
| 管理信息 Management | 谁负责、哪个版本有效 | 责任方、版本、审批状态、交付时间 |

“模型”并不只是一个三维壳体，更加准确的定义是

> **以工程对象为核心，把几何、属性、分类、关系、状态和管理过程组织起来的信息模型，以及围绕这些信息模型建立的一套生产、交换、审核和协同机制。**

### BIM ≠ 三维

工程天然具有空间属性，三维也确实是 BIM 非常重要的一部分。二维图纸需要人脑把平面图、立面图、剖面图重新组合成空间关系；三维模型则可以直接表达：

- 构件的位置；
- 尺寸与形状；
- 空间占用；
- 设备之间的相对关系；
- 碰撞与净距；
- 施工空间；
- 运维检修空间。

但如果一个模型只有漂亮的几何，没有稳定的构件 ID、分类、属性和关系，那么它更接近**3D 模型**，而不是完整意义上的工程信息模型。反过来，即使某些信息没有复杂的三维表达，只要它被明确地关联到工程对象，也仍然可以是 BIM 信息的一部分。

一个判断方法是：**如果关闭三维窗口，这套数据还剩下多少工程价值？**

如果关闭三维以后，设备名称、编码、分类、类型、参数、空间关系、文档关联、版本和状态全部消失，那么这个系统的核心可能仍然是三维展示。

如果关闭三维以后，工程对象及其信息仍然可以被查询、校验、交换和管理，那么它才真正接近“信息模型”。

---

### 三种不同视角

**不同角色说的“BIM”，其实不是同一个关注点。**至少可以区分三个典型视角。

#### 模型设计者

模型设计者关心的是怎样正确表达工程对象，例如：

- 对象应该建成什么类别？
- 几何精度做到什么程度？
- 什么信息放在类型上？
- 什么信息属于具体实例？
- 应该包含哪些属性？
- 对象之间如何建立关系？
- 模型怎样满足交付要求？

例如，对于一台主变压器，模型设计者需要思考：

```text
主变压器
├─ 几何
├─ 类型
│  ├─ 设备型式
│  ├─ 产品型号
│  ├─ 额定容量
│  └─ 额定电压
├─ 实例
│  ├─ 设备编码
│  ├─ 出厂编号
│  └─ 安装位置
├─ 分类
└─ 与站点、系统及其他设备的关系
```

这里需要注意：某个字段究竟映射为 IFC Type、Property Set 还是外部分类，并不存在脱离具体标准和企业建模规范的绝对答案。重要的是先理解：

> **共享于同一类设备的信息，与某一个具体设备实例的信息，是两个不同层次。**

---

#### 模型应用者

对于工程管理人员，关心的是这些信息能解决什么工程问题。例如数字化移交时，更自然的问题是：

- 我到底需要什么信息？
- 为什么需要这些信息？
- 谁负责生产？
- 什么时间需要？
- 谁负责审核？
- 怎么判断是否满足要求？
- 模型信息和设备台账、物资系统、试验系统是什么关系？

> “这个业务场景究竟需要什么可信的信息？”

只有需求被定义清楚以后，才轮到模型设计和软件实现。

---

#### 软件开发者

开发者看到的 BIM 又是另一套问题，怎样把工程信息变成可计算、可渲染的数据：

- IFC Schema 如何组织？
- 一个对象如何找到 Type？
- PropertySet 在哪里？
- Spatial Relationship 怎么遍历？
- 几何 Representation 如何解析？
- GlobalId 如何保持稳定？
- IFC 如何转换成浏览器能够高效渲染的数据？
- 模型属性存数据库还是保留在 IFC 中？
- 怎么做模型版本比较和增量更新？

开发者最容易犯的错误是：把 BIM 当成一种特殊的 3D 文件格式。实际上，IFC 的价值并不仅仅是“保存三角面”。它更重要的部分是：

> **工程对象、属性、分类、空间结构和关系组成的语义数据图。**

因此，BIM Viewer 和普通 3D Viewer 或者游戏引擎 的本质区别，不是能不能打开 IFC，而是：**它是否理解工程对象。**

## 二、BIM 标准体系

### 1. ISO 19650

ISO 19650 首先不是教你怎么画模型，而是信息应该怎样被管理。

> **在建设资产全生命周期中，信息怎样被组织、生产、审核、共享和交付。**

具体包括：

- 信息需求；
- 责任；
- 工作流；
- 信息容器；
- 状态；
- 版本；
- CDE；
- 交付与审批。

因此，可以先把 ISO 19650 看成 BIM 世界中的：**信息管理框架。**

---

### 2. OIR / AIR / PIR / EIR

不同层次的信息需求，可以逐步向项目和交付任务传递。可以先用一个简化理解：

```text
组织目标
  ↓
OIR —— 组织为了管理业务，需要什么信息
  ↓
AIR / PIR
  ├─ AIR —— 为资产管理需要什么信息
  └─ PIR —— 为某个项目管理需要什么信息
  ↓
EIR —— 某次信息交换或交付，需要提供什么
```

对于建设单位而言，这一步尤其重要。因为“所有东西都建进模型”通常不是合理目标。真正的问题应该是：

> **为了某个业务决策，我需要哪些信息？**

---

### 3. IDM

IDM（Information Delivery Manual）的价值，可以用四个问题概括：

> **为什么交？谁交？何时交？交什么？**

例如：主变压器数字化移交常见

**为什么交？**为了竣工验收、设备建账和后续运维。

**谁交？**设计单位、设备供应商、施工单位、试验单位分别产生不同的信息。

**什么时候交？**不是全部等到工程结束才交，而是在设计、设备采购、安装、调试、竣工等节点逐步形成。

**交什么？**包括：设备身份、类型、主要参数、空间位置、安装信息、试验信息、关联文档、最终竣工状态。

这一步与 IFC无关，仅关注业务交换逻辑想清楚。

> **模型标准应该服务于业务，而不是让业务去迁就模型格式。**

---

### 4. IDS

IDS（Information Delivery Specification）解决的是：**把信息交付要求变成机器可读取、可验证的规则。**

例如：

> 每一台主变压器都必须具有设备编码、额定容量和额定电压。

人看到这句话可以理解。IDS 的目标则是让软件也能够理解，并自动回答：

```text
模型中有哪些主变压器？
每一个有没有设备编码？
有没有额定容量？
有没有额定电压？
值是否符合预期的数据类型和约束？
```

> **IDM 更偏“业务交换过程”，IDS 更偏“可机器检查的信息要求”。**

---

### 5. IFC

IFC（Industry Foundation Classes）是 openBIM 体系最核心的数据标准之一。刚开始接触 IFC 时，很容易把它理解成：BIM 领域的 `.dwg` 或 `.obj`

但这种理解过于狭窄。IFC 更接近：**一套描述工程对象及其关系的数据模型，同时具有文件交换表达。**

它不仅描述：

```text
一个东西的几何
```

还描述：

```text
它是什么对象
它属于什么类型
它有哪些属性
它位于哪里
它和谁连接
它属于什么系统
它和其他对象是什么关系
```

所以学习 IFC 时，需要逐渐建立几个重要概念：

- Entity；
- Type；
- Occurrence；
- Property / Property Set；
- Classification；
- Spatial Structure；
- Relationship；
- Representation。

---

#### Type 与 Occurrence

假设一个变电站里有两台相同型号的主变压器。它们可能具有共同的信息：

```text
型号
额定容量
额定电压
设备型式
```

这些信息描述的是：**这一类设备是什么。**因此适合放在 Type 或共享类型信息中。

但每一台具体设备还有自己的信息：

```text
设备编码
出厂编号
安装位置
出厂日期
安装日期
投运日期
```

这些信息描述的是：**这一台具体设备是谁。**它们属于 Occurrence，也就是具体实例。

可以把它类比为软件开发：

```text
Type        ≈ Class / 类型定义
Occurrence  ≈ Object / 实例
```

---

### 6. bSDD

即使两个系统都保存了“额定容量”，也不代表它们一定在表达同一个概念。工程数字化经常遇到：

```text
系统 A：设备类型
系统 B：设备类别
系统 C：设备型式
系统 D：设备种类
```

这些字段可能相同，也可能完全不同。因此，BIM 不只是定义数据结构，还必须处理：**概念和语义的一致性。**

Classification 用来建立对象分类。

bSDD（buildingSMART Data Dictionary）进一步试图为术语、属性和分类提供可共享的语义字典。

它解决的是一个非常基础的问题：

> **不同参与方和不同软件说的“同一个词”，到底是不是同一个概念？**

---

### 7. BCF

BIM 不可能只有“模型正确”和“模型错误”两个状态。真实工程里会不断发生：

```text
发现问题
 ↓
定位对象
 ↓
描述问题
 ↓
责任方处理
 ↓
重新提交
 ↓
复核
 ↓
关闭
```

BCF（BIM Collaboration Format）用于表达这种基于模型的问题协同。它通常不需要复制整个 BIM 模型，而是记录：

- 问题；
- 相关对象；
- 视点；
- 截图；
- 评论；
- 状态；
- 责任信息。

可以类比软件开发中的：

> **Issue + Comment + 对代码位置的引用**

---

### 8. CDE

如果模型文件只是：

```text
设计院发一个
施工单位改一个
微信群再传一个
本地电脑还有五个
```

那么即使模型本身非常先进，信息管理依然是混乱的。CDE（Common Data Environment，共同数据环境）的核心并不只是：

> “大家都上传到同一个网盘。”

真正重要的是：

- 信息在哪里产生；
- 当前是什么状态；
- 谁可以修改；
- 谁可以共享；
- 谁负责审核；
- 哪个版本可以用于施工；
- 历史版本是否可追溯。

因此：

> **CDE 是受控的信息协同环境，而不是单纯的文件存储。**

BIM 要解决的不是“等所有东西不再变化以后再建模”，而是：**让变化处于受控状态。**

---

#### 版本和状态

真实工程绝不会一次形成一个完美模型。更合理的过程是：

```text
设计中
 ↓
阶段性共享
 ↓
专业协调
 ↓
审核 / 批准
 ↓
用于施工
 ↓
设计变更
 ↓
重新发布
 ↓
竣工模型
```

因此，一个模型文件不能只回答“这是哪个版本？”，还需要回答“这个版本现在可以拿来干什么？”

---

#### 权威数据源

既然 BIM 是信息模型，是不是所有工程数据都应该写进 BIM，并且以后全部在 BIM 里维护。答案是不一定，例如：

- 设备编码可能由资产管理系统管理；
- 物料信息可能来自物资系统；
- 厂家信息可能来自设备台账；
- 实时状态可能来自 SCADA / IoT；
- 文档可能由文档管理系统负责。

这些系统才是某些数据的：

> **Authoritative Source / System of Record**

BIM 可以携带这些信息，尤其是离线数字化交付时需要形成一个时间点的数据快照。

但如果进入在线系统，更合理的方式往往是：

```text
BIM 对象
   │
   ├─ 稳定身份
   ├─ 几何
   ├─ 空间与语义关系
   │
   └─ 引用 / 关联
          ↓
设备台账 / 文档 / IoT / 业务系统
```

这意味着：

> **权威数据源不等于 BIM 中绝对不能携带数据，但不应该无控制地形成多个可编辑的数据副本。**

这是从“模型交付”走向“数字孪生”时必须解决的问题。

---

## 四、 openBIM与工具

如果工程从设计到施工、验收和运维只依赖某一家软件厂商的内部格式，会产生一个明显问题：

> 信息生命周期往往比软件生命周期更长。

工程资产可能运行几十年。但软件、版本、供应商和平台都可能变化。因此 openBIM 的核心价值不是“免费软件”，而是：

> **通过开放、厂商中立的标准，让工程信息能够跨软件、跨参与方、跨阶段持续交换和使用。**

```text
openBIM
│
├─ buildingSMART —— 主要标准推动组织
│
├─ IFC —— 工程信息模型
├─ IDS —— 信息要求与自动检查
├─ BCF —— 问题协同
├─ bSDD —— 术语与语义
│
└─ 各类实现
   ├─ 商业软件
   └─ 开源软件
```
