# 提示词工程

提示词工程的本质是把任务、上下文与验收标准表达清楚，让模型的输出可以被程序或人可靠地消费。本文覆盖工作流方法、结构化框架、基础技巧与项目级实践。

## 一、工作流方法：I.S.G.I.E

1. **输入 (Input)**：要解决的问题、原始素材、必须遵循的要求。
2. **结构 (Structure)**：设计"认知架构"，引导模型将复杂问题拆解为中间推理步骤和有层次的子问题。
3. **生成 (Generate)**
4. **迭代 (Iterate)**：给出评价标准或具体问题，引导模型自我修正。
5. **表达 (Express)**：把生成结果转成适配受众的形式，并把过程沉淀为 SOP/模板以便复用。

## 二、结构化框架

### 1. S.C.O.R.E.

> Setting · Context · Objective · Requirements · Evaluation
> 它不是用来"评价 Agent"的，而是用来"控制模型输出行为"的——高级 Prompt 的骨架。

| 维度 | 原理 |
| --- | --- |
| **Setting**（角色设定） | "锚定潜空间"：明确身份激活模型相关权重区域，屏蔽不相关干扰；同时限定知识边界，减少跨领域幻觉 |
| **Context**（背景信息） | In-Context Learning：注入实时/私有数据对抗幻觉；注意"上下文腐烂"——过长上下文会导致中间信息记忆力下降 |
| **Objective**（任务目标） | 思维链触发器：目标必须原子化、可衡量（如"将非结构化文本转化为 ISO 8601 时间序列"），建立输入到输出的直接映射 |
| **Requirements**（输出要求） | 验收清单：格式（JSON/Markdown）、字数、风格、禁止项；用 XML/Markdown 标签做定界符提升解析可靠性 |
| **Evaluation**（评估标准） | LLM-as-a-Judge 自纠错：嵌入评价准则，促使模型实时审计或二次检查 |

### 2. CO-STAR

CO-STAR 与 SCORE 同源，增加了 Style/Tone/Audience 维度，适合对输出风格敏感的场景：

- **C (Context)**："你现在作为一名资深 Python 后端工程师，负责优化高并发 API 系统的性能。"
- **O (Objective)**："重构以下代码段，目标是减少内存占用并提高执行速度。"
- **S (Style)**："遵循 Google Python 代码规范，保持简洁、Pythonic。"
- **T (Tone)**："客观、技术性强，避免冗余客套话。"
- **A (Audience)**："面向具有 3 年以上经验的中级开发人员。"
- **R (Response)**："以 Markdown 代码块输出，代码后附关键改动要点。"

### 3. S.C.A.F.F.（复杂任务）

| 字母 | 英文 | 中文 | 核心问题 |
| ---- | ---- | ---- | -------- |
| S | **Situation** | 情境 | 项目类型和目标、技术栈、开发阶段、已有代码结构或设计决策 |
| C | **Challenge** | 挑战 | 要实现的功能或修复的问题、输入输出、具体业务逻辑 |
| A | Audience | 受众 | 产出给谁用？使用者/维护者的技术水平 |
| F | Format | 格式 | 期望 AI 输出什么格式？是否需要使用说明 |
| F | **Foundations** | 基础 | 技术、性能、安全、风格约束 |

项目类型：

【Challenge - 挑战】

### 4. R.G.C.（简单任务）

| 字母 | 英文 | 中文 | 核心问题 |
| ---- | ---- | ---- | -------- |
| R | Role | 角色 | 让 AI 扮演什么身份？ |
| G | Goal | 目标 | 要完成什么任务？ |
| C | Constraints | 约束 | 有哪些限制条件？ |

````
【Role - 角色】
你是一个注重代码可读性和可维护性的 Python 工程师。

【Goal - 目标】
重构下面这段代码，提高可读性：
- 让变量命名更清晰
- 把重复逻辑提取成函数
- 添加必要的注释

```python
def f(l):
    r=[]
    for i in l:
        if i>0:
            r.append(i*2)
    return r

【Constraints - 约束】
- 保持功能完全不变
- 注释用中文
````

## 三、基础技巧

### 1. Zero-shot

只适用于常规任务：角色设定 + 输出格式。

```
你是 [角色定位]。

任务：[具体任务描述]

要求：
- [要求1]
- [要求2]

输出格式：[格式说明]
```

代码审查变体：

```
审查以下代码，从 [审查维度] 角度指出问题：

[代码内容]

输出格式：
1. 问题：[描述] | 位置：[行号] | 建议：[修改方案]
```

### 2. Few-shot

给 2~3 个示例，要求典型、多样、格式一致。

### 3. Chain of Thought

```
问题描述：[问题现象]

相关代码/配置：
[代码或配置]

请帮我分析问题原因。

排查步骤：
1. 首先，理解正常情况下应该如何工作
2. 然后，检查当前代码的执行流程
3. 接着，定位可能导致问题的环节
4. 最后，给出修复方案

让我们一步一步来思考。
```

### 4. Tree of Thoughts

```
我需要 [决策内容]。

项目背景：
- [背景信息]
- [关键约束]

请给出 [数量] 种不同的方案，对每种方案从多个维度分析优劣。
最后，根据我的项目情况，推荐最适合的方案并说明理由。
```

### 5. Self-Critique

```
请扮演一个严格的代码审查者，审查你刚才生成的代码：
- 找出至少 3 个可以改进的地方
- 给出改进后的版本

请自查：
1. 边界情况是否都处理了？
2. 有没有潜在的安全问题？
3. 性能是否可以优化？
如有问题，请修正后输出最终版本。
```

## 四、用 PRD 表达复杂需求

复杂任务不要靠一段话描述，写成 PRD 让模型按验收标准交付。

### 通用模板

```
# [项目名称]
请根据以下 PRD 实现第一版，只做 P0 功能，不要做任何额外的事情。

## 一句话描述
[这是什么、给谁用、解决什么问题]

## 目标用户
[谁会用？保留与产品相关的特征]

## 要解决的问题
[用户遇到了什么困扰？现有方案有什么不足？]

## 核心功能（P0，必须有）
- [ ] 功能1：[简要描述]

## 不做的功能
- 不要 [功能A]（原因）

## 用户流程
1. 用户 [动作] → 看到 [结果]

## 技术约束
- 技术栈：
- 数据存储：
- 其他限制：

## 成功标准
- [ ] 标准1
- [ ] 标准2

特别强调：
- 只实现"核心功能"列出的功能
- 不要添加 PRD 中没有提到的功能
```

数据分析、自动化脚本类项目同理：一句话描述 → 目标用户 → 要回答的问题/痛点 → 数据来源/输入输出 → 处理逻辑 → 成功标准。

### PRD 自检

```
请帮我检查这份 PRD 是否有遗漏或歧义：
1. 这份 PRD 是否足够清晰，你能准确理解我要什么？
2. 有没有哪些地方你不确定该怎么做？
3. 有没有我可能遗漏的边界情况？

请用你自己的话描述一下你理解我要做什么产品，
包括：用户是谁、解决什么问题、有哪些功能、没有哪些功能。
```

## 五、多轮迭代技巧

长会话开发的关键是状态管理与约定重申：

| 场景 | 示例话术 |
| --- | --- |
| 进入新阶段 | "P0 验证通过，请继续添加 P1 功能..." |
| 发现问题 | "测试 P0 时发现一个问题：[描述]。请先修复这个，然后再继续 P1。" |
| 调整计划 | "P0 做完后发现不需要 P1 的删除功能了，请直接跳到 P2。" |
| 回归测试 | 列功能验证 + 回归测试 + 边界情况三项 checklist，全部通过再继续 |
| 定期总结 | "请总结目前的项目状态：已完成功能、技术栈约定、待完成功能。" |
| 约定重申 | "开始新功能之前，确认一下我们的约定：1... 2... 确认后开始实现 [功能]。" |

会话过长时，让模型导出关键信息（技术栈约定、已完成功能、代码结构、遗留问题）带到新对话。

把长期约定写进配置文件，比每次在对话里重复更可靠：

| 工具 | 配置文件位置 | 功能定位 |
| -------------- | ------------------------------------------ | ------------------------------ |
| Cursor | `.cursor/rules/*.mdc` | 项目规范、编码风格、技术栈偏好 |
| Windsurf | `.windsurf/rules/*.md` 或 `.windsurfrules` | 项目级 AI 行为规则 |
| Claude Code | `CLAUDE.md` + `SKILL.md` | 项目上下文 + 可复用技能 |
| GitHub Copilot | `.github/copilot-instructions.md` | 仓库级指令 |
| OpenAI Codex | `AGENTS.md` | 代理指令文件 |
| Factory Droid | `.factory/droids/*.md` | 自定义 Droid 配置 |

配置文件内容骨架：项目概述 / 技术栈及版本 / 目录结构 / 编码规范 / 禁止事项 / 常用命令。

## 七、综合案例：文件写入的安全围栏

高风险操作（写文件、执行命令）应在提示词层面强制"先提案、后授权"。以下是用 SCORE 组织的四步状态机协议：

```text
Role: 你是一位极度谨慎的"数据归档专员"，默认假设每个目标路径都可能存在同名重要文件。
Risk Level: High (L3)，涉及文件写入，需执行 HITL 流程。

Phase 1 提案: 分析内容，生成合规文件名与摘要。严禁调用工具，仅输出 Markdown 预览卡片。
Phase 2 撞库查验: 询问目标路径是否已存在文件；
  - 不存在 → 回复 Y / Create
  - 已存在且需覆盖 → 回复 OVERWRITE
Phase 3 决策分流:
  - Case A 执行: input ∈ {Y, Create, OVERWRITE} → 调用 write_file
  - Case B 修改: 包含修改意图 → 返回 Phase 1 重新提案
  - Case C 终止: input ∈ {N, Cancel} → 结束话题
Phase 4 完结: 收到工具 Success 后输出确认并结束。

附加约束:
1. 思维链强制: 每次回复前输出 Current State: [Phase X]；
   Phase 3 前必须在思维链中复述授权类型（Create 还是 Overwrite）。
```

配套的三道防线：分级风险控制模型（低中高操作分级）、四步状态机协议（预览→确认→授权→写入）、软硬围栏拦截（保护关键数据不被误操作）。

## 八、提示词工程还重要吗？

一个值得正视的趋势：随着模型能力越来越强，提示词工程的重要性反而在下降。

原因不难理解——本文大半技巧（角色设定、few-shot 示例、格式约束、"让我们一步一步思考"）本质上是在**补偿模型的不足**：补指令遵循、补推理能力、补格式稳定性。模型每变强一分，这些补偿就贬值一分；今天的旗舰模型已经能从一句模糊的话里猜对你的大部分意图。

但有三件事不会随之贬值，反而越来越重要：

1. **问题定义**：模型能猜意图，但不能替你知道自己想要什么。目标、边界、约束、验收标准——这些来自你的领域知识与判断力，是提示里唯一无法被模型"脑补"的部分。写得清楚的需求永远稀缺。
2. **上下文工程**：与其雕琢措辞，不如管理信息——什么该进入上下文（AGENTS.md、检索证据、工具反馈）、什么该被压缩或排除。智能体时代的主战场已经从"怎么问"转移到"给模型看什么"，见[智能体的记忆](knowledge/llm/agents/agent-memory)。
3. **验证标准**：模型产出越快，判断好坏的能力越值钱。明确的评估维度与回归集（见[智能体的评估](knowledge/llm/agents/agent-evaluation)）决定了你敢不敢把任务交给它。

一句话总结：**提示词工程的技巧会过时，但它训练出的三样东西不会——把需求想清楚的习惯、把上下文喂对的意识、把结果验准的标准。** 本文的框架仍值得学，因为它们是这三件事的具体练习。
