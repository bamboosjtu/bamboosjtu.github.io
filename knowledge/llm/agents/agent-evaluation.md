# 智能体的评估

智能体工程与普通软件开发最大的差异，在于"改好了还是改坏了"经常说不清：模型有随机性、路径有多步性、失败是概率性的。评估因此不是锦上添花的测试环节，而是智能体开发的主循环本身——没有评估的优化只是玄学调参。

## 一、先让系统可观察

评估的前提是看得见。智能体运行过程中每一步的中间输出集合称为**追踪 (trace)**，单步输出称为 **span**。可观测性的三大支柱对 agent 同样成立：

| 支柱 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| Logs | 发生了什么？ | 每次模型调用、工具执行、错误事件 |
| Traces | 一次任务的完整路径是什么？ | 步骤序列、每步输入输出、耗时、token 用量 |
| Metrics | 系统长期表现如何？ | 成功率、平均步数、成本/任务、P95 延迟 |

主流框架都已内建追踪能力（LangSmith、OpenAI Agents SDK 的 Trace Viewer 等），行业也在向 OpenTelemetry 标准收敛。实践建议从第一天就记录 trace——事后无法补采。

## 二、两类评估方法

拿到 trace 之后，如何判断质量好坏？

| 评估维度             | 客观评估（Objective Evals）  | 主观评估（Subjective Evals）          |
| -------------------- | ---------------------------- | ------------------------------------- |
| 有每个例子的基本事实 | 用代码检查是否匹配           | 用 LLM 检查是否充分提及               |
| 无每个例子的基本事实 | 用代码检查是否符合统一标准   | 用 LLM 打分（Rubric Grading）         |

- **端到端评估**把 Agent 视为黑盒，度量最终任务完成质量——它回答"系统整体行不行"；
- **组件评估**隔离测试单个模块（检索器、规划器、某个工具）——它回答"坏了该怪谁"。

主观评估中，LLM-as-a-Judge 是目前最实用的折中：用强模型按明确的评分维度（rubric）给输出打分。它的关键是 rubric 本身要具体——"回答好吗"是无效标准，"是否引用了检索到的证据、是否存在编造的数字"才是。

## 三、错误分析：找到最值得修的地方

错误分析的核心是观察和量化，而不是猜测：

1. **检查追踪**：通览失败案例的完整 trace，笼统判断哪个组件出了问题；
2. **聚焦错误**：把精力集中在最终输出不令人满意的少数案例上，而不是运行良好的案例；
3. **定义错误**：某一步的输出明显差于人类专家在相同输入下的结果，才算错误；
4. **量化归因**：统计所有错误案例中"搜索词不佳占多少、检索结果不佳占多少、格式解析失败占多少"，最大的桶就是最优先的改进目标。

## 四、改进的正确顺序

### 1. 非 LLM 组件

- 调整参数或超参数：搜索结果数量、日期范围；RAG 相似度阈值、分块大小；检测阈值权衡误报漏报；
- 替换组件：更换搜索引擎、Web API 或向量库，用组件级评估对比择优。

### 2. LLM 组件

- 改进提示词：增加明确指令和资源指引（而不是让模型自己猜）；添加少样本示例；
- 更换模型：多测几款，用 evals 选择最适合特定应用的一个；
- 任务分解：单步指令过于复杂时，拆成生成 + 反思两步，或拆成多次调用；
- 微调：最复杂、成本最高的选项。只有穷尽其他方法后仍需挤出最后几个百分点性能时才考虑。

顺序很重要：先修便宜的、确定性的部分，再动提示词，最后才考虑换模型和微调。

## 五、延迟与成本

### 1. 延迟

- **计时分析**：详细记录每个步骤耗时（如：LLM 1 耗时 7 秒，LLM 3 耗时 18 秒）；
- **定位瓶颈**：时间线上耗时最长的组件就是最大提速空间；
- **优化手段**：独立步骤并行化（如网页抓取）；更换更小更快的模型或更快的提供商；利用 prompt caching 减少重复前缀的计算。

### 2. 成本

- **逐项计费**：LLM 按输入/输出 token 计费，API 按调用次数计费，计算与服务按容量计费；
- **定位大头**：确定成本贡献最大的组件再动手；
- **常见杠杆**：压缩上下文历史（见[智能体的记忆](knowledge/llm/agents/agent-memory)）、廉价模型跑简单步骤 + 强模型只做关键决策、缓存高频查询结果。

## 六、建立回归集

单次评估没有意义，趋势才有意义。把每次发现的真实失败案例转化为测试用例，逐步积累成回归集：

```text
新改动 → 跑回归集 → 对比成功率/成本/延迟 → 通过则合入，退化则回滚
```

这与传统软件的 CI 思想一致，只是断言从"函数返回值正确"变成了"任务完成度达标"。回归集是智能体从 demo 走向生产的最重要标志。
