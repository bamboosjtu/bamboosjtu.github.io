# 瑞数6初探

> 本文整理自对某网站动态防护的一次完整逆向学习。站点信息、业务系统与具体参数已做脱敏处理，一律以"某网站""业务客户端"代称；保留的是方法论骨架——它适用于所有同类动态防护的分析。

## 一、瑞数防护的工作方式

瑞数（RiverSecurity）是国内常见的动态防护产品。以第 6 代为例，访问受保护站点时的典型流程：

```text
首次请求 ──→ 服务器返回 412 + 一段动态生成的 JS（外层 VM + 配置数据）
        ──→ 浏览器执行 JS，计算并写入 Cookie
        ──→ 自动重放请求（携带新 Cookie）
        ──→ 服务器校验通过，返回真实页面（内含另一层 VM）
        ──→ 内层 VM 持续参与后续请求的合法性校验
```

关键观察：这是**两次交互**模型——第一次拿"材料"，执行后换"通行证"。逆向的目标是让程序脱离浏览器完成同样的计算，即所谓**纯算路线**。

## 二、阶段 1：VM 提取

使用开源工具链 [rs-reverse](https://github.com/zhaoboy969/rs-reverse) 的 `makecode-high` 命令（专为两次交互站点设计）对目标 URL 执行提取，得到两层产物：

| 目录 | 内容 | 特点 |
| --- | --- | --- |
| `first/` | 外层 VM 代码 + 还原后的动态代码 + `$_ts` 数据（完整/精简）+ immucfg 静态配置 | **每次请求都变化** |
| `second/` | 内层 VM 代码 + 同构的四类文件 | **永远不变** |

三条关键结论：

1. **内层 VM 是固定的**——多次提取后 hash 完全一致，可以永久缓存；
2. **`$_ts` 要区分动静**：`nsd`、`cd`、字节码数组 `scj/aebi` 每次变化；`cp[0..2]` 是静态代码片段，`cp[3]` 是随时间变的 hash、`cp[4]` 是时间戳；
3. **两层的 immucfg（globalText 等代码模板）互不相同**，必须分别保存。

这一阶段的工程习惯值得强调：每一步都有**验证清单**（文件可读、结构完整、动态代码可还原、hash 可复现），而不是"跑通了就行"。

## 三、阶段 2：沙箱调试

在 Node.js 里补齐浏览器环境（window/document/navigator 等），把 `currentScript` 正确绑定后运行提取出的 VM。沙箱的价值在于：让 VM 在可观测、可插桩的环境里跑起来，同时记录它对外部环境的全部依赖——这些依赖就是后面纯算方案需要模拟的面貌。

## 四、阶段 3：定位核心计算逻辑

内层 VM 经过重度混淆（VMP 字节码），字符串和 API 调用都被编码，无法通过文本搜索定位。正确的方法是**运行时 Hook**：

```text
Hook document.cookie setter → 定位 Cookie 写入点
Hook Date.now              → 统计时间戳使用
Hook Math.random           → 排查随机来源
Hook navigator.userAgent   → 定位指纹采集
```

实测发现（某网站样本）：Cookie 分**两次写入**——先写一个 `enable_` 开头的标志位，再写入约 200 字符、以 `.` 分段的主值；`Date.now` 被调用 11 次（反调试计时/随机种子/过期计算）；`navigator.userAgent` 被读取 4 次（环境指纹）；`Math.random` 直接调用为 0 次（随机性来自 crypto 或间接路径）；VM 本身不发起网络请求。

### 六层解释器结构

动态还原后的代码呈现清晰的解释器套娃：

| 层级 | 角色 |
| --- | --- |
| 入口匿名函数 | 接收 `$_ts.scj / aebi` 字节码 |
| 大量辅助小函数 | 每个只封装一个 opcode 数字，转发给主解释器 |
| 主解释器 `_$hU` | opcode 分派中枢 |
| 三至六层次级解释器 | 逐级下沉处理具体操作 |

这解释了为什么静态分析几乎不可能：指令流存在数据里（`$_ts.aebi`），每次请求的字节码都不同。

### Cookie 生成流程推测

综合观察推断：采集指纹（UA 等）→ 取时间戳 → 生成基础数组（结合 `$_ts`）→ 异或/哈希等编码 → 两次写入 Cookie → 清空 `$_ts` 自我保护。其中若干环节（国密算法、CRC 校验）属于待确认的推测，但流程骨架与开源纯算实现相互印证。

## 五、阶段 4–5：纯算路线与生成器封装

还原关键函数有两个方案：

- **方案 A：纯函数翻译**——把逻辑翻译成独立代码，彻底摆脱 VM；
- **方案 B：VM 封装**——在受控环境里直接驱动 VM。

实践建议是**先 B 后 A**：先用方案 B 快速验证整条链路，再逐模块迁移。纯算框架要解决三个典型问题：模块路径别名解析、VM 运行时篡改 `$_ts` 导致的失效、以及内部随机性带来的输出差异——因此**一致性验证是生命线**：同一输入下，纯算输出与浏览器真实输出必须逐字节可比对。

验证通过后封装成独立的生成器类（如 `Rs6Generator`）：输入 URL 与配置，输出可用 Cookie。一个重要的 API 设计决策是把"增量 Cookie"与"完整 Cookie"分开返回——前者用于追加到已有会话，后者用于全新会话，混用一个接口会让调用方陷入状态混乱。

## 六、阶段 6：业务集成

最后一步是把生成器接进业务客户端：

- **Cookie 管理**：会话初始化时生成并通过校验；
- **412 自动处理**：收到 412 时自动走一次挑战流程再重放，对上层透明；
- **请求重写**：在统一出口处附加合法参数，避免每个业务调用各自处理。

到这里，程序可以在完全不启动浏览器的情况下，稳定地通过该站的动态防护并完成数据请求。

## 七、方法论复盘

整个六阶段过程比任何单项技巧更值得学习：

1. **阶段化推进**：每阶段有明确目标、产物清单与验证标准，完成后才进入下一阶段；
2. **先黑盒后白盒**：先 Hook 观察行为（写了什么 Cookie、读了哪些环境变量），再深入解释器结构；
3. **一切皆验证**：VM 提取看 hash、纯算看一致性、集成看回归——没有"看起来对了"；
4. **区分动静**：把不变的部分缓存起来，把变化的参数化，是应对"每次请求都不同"这类防护的根本思路。
