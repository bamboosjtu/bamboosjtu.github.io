# 本体论 or 数据中台外包商

最近一两年，国内企业数字化领域突然开始密集讨论 Palantir。

以前的关键词是数据湖、数据中台、主数据、知识图谱，现在换成了 Ontology、本体、企业数字世界、AI Native。有些方案甚至已经不满足于“借鉴 Palantir”，而是直接宣布自己要建设“中国版 Palantir”。

然后翻到实施方案，看到的通常还是那套熟悉的方法：组织业务专家访谈，梳理业务对象，定义实体、属性和关系，形成企业本体模型；再把几十套业务系统的数据库表和接口映射进来，在上面做几个驾驶舱、智能问答和 Agent。

如果再把技术名词全部拿掉，它和十年前的数据中台项目没有太大区别。以前交付的是主题域模型、指标体系和数据资产目录，现在交付的是 Object、Property、Link。以前做的是统一数据模型，现在叫企业 Ontology，毕竟`本体论`这个名词看起来就很洋气。

## Palantir 的 Ontology 可不是 ER 图

Palantir 自己在 2026 年的 Foundry 技术说明中甚至专门强调：**“The Ontology is not a semantic layer.”** 它把 Ontology 描述成数据、逻辑、动作和安全四类东西共同构成的运行层。Object 和 Link 只是其中一部分，还有 Action、Function、权限体系，以及从业务操作写回外部系统的机制。它给出的典型数据流也不是“源系统→数据中台→本体→大屏”，而是“源系统→数据→Ontology→应用→用户决策→Action→写回外部系统”。

这个区别非常重要。如果我们把 Ontology 理解成“把数据库里的表翻译成业务能看懂的对象”，那么它确实很容易退化成知识图谱或者语义层。设备表变成 Equipment，项目表变成 Project，人员表变成 Employee，再把外键包装成 Link，技术工作基本就完成了。

但在 Palantir 的定义中，“设备”只是名词的一半。真正重要的另一半是：谁可以修改设备状态，什么条件下可以生成维护任务，什么模型可以判断风险，什么动作能够触发 SAP 工单，谁有权限执行这个动作，执行以后其他应用能否立即看到结果。

换句话说，它想解决的不是“企业的数据是什么意思”，而是“企业基于这些数据如何做决定，并且如何把决定执行下去”。

## 看一个真实案例：Palantir 怎么做变压器故障管理

Palantir 官方文档公开过一个北美公用事业公司的案例。虽然这是厂商自己的案例材料，效果数字应当按厂商口径理解，但它至少非常清楚地展示了 Foundry 的实施方法。

这家电力企业希望做风险导向的资产管理。问题非常典型：设备台账、停电记录、检修记录、传感器、气象、地理信息散落在不同系统里，而且彼此可能矛盾。业务人员真正需要解决的问题也非常具体——哪些变压器风险最高，哪些应该优先检查，某次停电到底是什么原因，维护资金应该优先花在哪里。

Palantir 没有从“请专家先定义一套完整电力企业本体”开始。它首先围绕这个使用场景，把九个不同系统的数据整合起来，包括地理空间、气象、设备、停电、调查、维护等数据；其中 GIS 被明确作为资产位置的记录系统，SAP 提供工单和检查数据，其他传感器、环境和停电数据继续补充这个资产视图。不同系统如果对同一次停电记录了不同原因，系统甚至会把这种冲突直接暴露出来，而不是假装经过一次“标准化”以后世界就只剩一个正确答案。

在这些数据之上，才形成导线、变压器、开关等对象，以及它们与停电、环境、检查、维护记录之间的关系。随后再构建面向具体工作人员的 Workshop 应用：工作人员不是进入一个“企业本体管理平台”浏览节点，而是直接看到待调查的异常、设备历史、地图位置和环境上下文，然后完成故障调查和决策。

最关键的是最后一步。调查人员做出的判断以及判断时的上下文，会通过应用直接写回。也就是说，“这台变压器需要检查”“这次停电原因判断为什么”“下一步采取什么措施”不是写在邮件、Excel 或微信群里，而重新变成系统中的数据，并进入下一轮分析和风险模型。Palantir 把这称为 learning loop。

这才是理解 Palantir Ontology 的钥匙。

它不是先试图回答一个哲学问题——“一家电力公司的完整本体是什么？”——而是先回答一个操作问题——“工作人员每天必须做出的这个决定，需要哪些对象、数据、规则和动作？”

Palantir 自己的开发方法文档写得更加直接：先定义一个有明确用户和业务结果的 use case，再分解功能需求；界面和数据富化需求反过来决定 Ontology 的设计，Ontology 在这里甚至被称为这个 use case 的 API。

这和国内大量“先建企业级本体，再赋能 N 个业务场景”的项目逻辑，方向几乎完全相反。

## 最荒诞的国产做法：让业务专家重新梳理系统

国内很多项目当然也会说：“本体必须来自业务。”

这句话本身没有错，但接下来通常就错了。

厂家会召集设备专家、生产专家、营销专家、项目管理专家，拿着 Excel、白板或者本体建模工具，开始问：“老师，我们这个业务里面有哪些核心对象？”“设备有哪些属性？”“设备和项目是什么关系？”“什么叫在运设备？”“这个状态是怎么变化的？”

听起来非常尊重业务，但只要稍微回顾一下过去二十年的企业信息化建设过程，就会发现这个场景非常荒诞。

今天所谓“遗留系统”里的数据库是谁设计的？厂商。接口是谁设计的？厂商。页面字段是谁安排的？厂商。很多状态机、编码规则、校验逻辑、流程跳转又是谁真正落实成软件的？还是厂商。

业务专家参与过需求讨论，但绝大部分业务语义最后不是以机器可理解的形式留在企业手中，而是被压进数据库结构、Java 代码、存储过程、接口参数和系统页面里。几年以后原来的实施团队早就撤场，设计文档也已经失真，只剩下一套还能运行的软件。

这时候下一代数字化厂商进场，说我们现在进入 AI 时代，需要构建企业 Ontology。然后他找到业务专家，让业务专家重新告诉他：“这个系统到底是什么意思”。

于是出现了中国企业数字化建设中特别有讽刺意味的一幕：**上一代软件厂商把业务知识编码进了一个黑盒；下一代软件厂商再要求业务专家通过使用这个黑盒的经验，把里面的业务知识口述出来。**

这已经不是普通的需求调研，而是一种**业务专家参与的肉身逆向工程**。业务专家每天知道应该点哪个按钮、什么时候提交、哪个字段不能填错，但他通常不知道这个页面背后读了哪六张表，不知道某个“设备状态”是原始字段还是 SQL 拼出来的，不知道两个系统里的“项目编号”到底是不是同一个主键，更不知道十年前某个开发人员为什么在代码里加了一条特殊判断。

新厂商于是把业务专家的记忆、数据库字段、接口返回值和现有页面重新拼起来，最终形成一份新的对象模型。然后宣布：“企业本体建设完成。”

## 构建企业本体还是人工反编译上一代信息系统

真正的问题不是使用业务专家。Palantir 也明确要求 Subject Matter Expert 参与，而且其定义恰恰是熟悉遗留工具、业务流程及其缺陷的高级用户。问题是专家在整个过程中的角色。

在一个合理的技术体系里，专家应该负责**语义裁决**。系统已经从数据库 Schema、API、数据血缘、运行日志、代码、界面行为中获得大量候选事实，然后向专家提出具体问题：“资产系统和检修系统里的这两个 ID 是否代表同一个设备？”“GIS 是否是位置的权威源？”“这个状态变化是否代表真实业务事件？”专家回答这些问题，是在确认机器从现有系统中发现的事实。

而很多国内项目干的恰恰相反。技术系统几乎不负责发现，而是把发现工作整体外包给人。厂家坐在会议室里问：“老师，请从头给我们讲一下设备管理业务”。这实际上是在让业务专家充当遗留软件的人肉反编译器。

更严重的是，即便这次反编译成功了，成果通常还是另外一套静态配置。业务系统继续运行，用户继续在原来的 ERP、生产系统、项目系统里操作，Ontology 平台则通过 ETL 定时同步这些结果。于是所谓“企业本体”天然滞后于真正的企业。业务发生在 A 系统，本体第二天同步；状态变化发生在 B 系统，本体再做映射；新系统上线以后，再申请接口、增加字段、修改映射。最终企业又多出了一套需要专门团队维护的数据基础设施。

这不就是数据中台吗？只是以前维护的是主题模型和指标口径，现在维护的是 Object 和 Link。

## Palantir 的建模方法论

这里也没有必要神化 Palantir。Palantir 自己公开的另一个欧洲电力企业案例反而很有意思。为了把 PSI 控制系统与 GIS 等数据统一成电网拓扑数字孪生，第一版本 Ontology 大约用了 12 个月。里面包括数以万计的坐标、电网设备、电缆、回路及其关系。后来，这套能力被产品化为可复用的 library，同类部署才缩短到数周。这个案例恰好说明，本体不存在什么神奇的自动生成按钮。

复杂企业的现实世界确实很难建模，数据冲突确实需要治理，业务专家确实要参与。Palantir 并没有绕过这些脏活累活。真正值得关注的是它怎样处理这些成本。第一套电网模型花一年没有关系，只要下一套电网不再从零开始；第一个停电调查工作流需要大量专家知识没有关系，只要最终沉淀的不只是一个项目文档，而是对象模型、数据管道、Action、Function、应用组件以及可重复使用的行业模式。这是一种产品化逻辑。

而传统外包逻辑恰恰相反。每来一家新客户，重新调研；每到一个新省份，重新梳理；每增加一个场景，重新召开业务研讨会；每换一家厂商，再重新解释一遍原来的系统。项目经验存在工程师脑子里，而没有真正进入产品。所以同样都有实施人员，同样都有业务专家，同样都做数据治理，两者最终形成的经济模型完全不同。

一个希望**第一次很贵，以后越来越便宜**。另一个恰恰依赖**每一次都很贵**。这恐怕也是为什么大量传统数据中台外包商即使学会了 Ontology 这个词，也很难真正成为 Palantir。

## 国产本体平台的谬误之处

Palantir 的逻辑大致是：有一个高价值业务问题，于是需要一个工作流；工作流需要操纵某些现实对象，于是定义这些对象；对象需要来自多个系统，于是建设数据管道和身份映射；决策需要落地，于是定义 Action、Function 和权限；用户每天在这个工作流里继续操作，新的决策和状态不断进入系统，Ontology 因而逐渐丰富。

很多国产方案则是：企业要建设 AI 能力，所以需要 Ontology；为了建设 Ontology，所以先进行全业务梳理；为了全业务梳理，所以组织大量访谈；访谈结束以后建设企业级模型；模型建成以后，再问各业务部门：“大家有什么场景可以用？”

两套路线都能画出漂亮的对象关系图。但它们的工程哲学完全不同。前者的 Ontology 是业务运行产生的基础设施。后者的 Ontology 是咨询项目生产的交付物。这也是我认为目前所谓“国产 Palantir”最值得警惕的地方。我们可能又在重复数据中台时代已经发生过一次的错误：先相信存在一个抽象、完整、统一的企业数据世界，然后花几年时间建设它，最后再努力寻找足够多的场景证明这笔投资有价值。

只是过去那个世界叫“企业数据资产”，今天换了一个更加时髦的名字：“企业本体”。

## 数据库和接口是最重要的考古现场

很多 Ontology 项目对现有系统本身研究得远远不够。事实上，一家运行了十几年甚至几十年的企业，其真实业务知识早已大量沉淀在软件中。数据库主键表达对象身份，外键表达关系，状态字段表达生命周期，唯一约束表达业务规则，接口参数表达动作所需的上下文，页面按钮表达允许的业务操作，权限配置表达什么人能干什么，工作流定义状态如何迁移，代码中的判断条件则保存着大量从未写进制度的实际规则。

这些东西当然不能直接等同于现实世界。遗留系统中有大量历史包袱、错误设计和厂商方言。但它们至少是**证据**。制度文件是证据，数据库是证据，接口是证据，代码是证据，用户操作日志是证据，业务专家也是证据。

真正的企业 Ontology 应该是这些证据相互校验之后形成的运行模型。而不是把其中最昂贵、最稀缺、最不结构化的一种证据——业务专家的时间——当成主要输入源。

AI 时代尤其如此。今天我们已经拥有足够强的代码理解、Schema 分析、API 分析、界面理解、日志分析和语义匹配能力，却仍然让几十位高级业务专家围坐在会议室里，从 Excel 第一行开始填写“对象名称、对象定义、属性名称、属性定义”。从技术上说，这不是先进。只是人工便宜的时候形成的项目实施习惯，延续到了人工智能时代。

## 业务梳理——AI时代最应该淘汰的术语

我认为 AI 时代最应该被淘汰的数字化术语之一，就是“全面梳理”。

不是说不需要理解业务，而是理解业务的方法必须变化。机器应该首先从现有数字系统里提取候选世界：有哪些稳定存在的对象、哪些 ID 在系统之间流转、哪些接口改变状态、哪些页面触发动作、哪些字段长期共同出现、哪些系统实际上拥有某类数据的最终控制权。然后让业务专家处理机器无法决定的问题。

这个顺序非常重要。未来合理的比例应该是：机器完成 80% 的发现、比对和候选建模，专家完成剩下 20% 的判断与裁决。而不是十几个专家完成 80% 的口述，厂家再把这些口述录入一个号称 AI Native 的平台。否则所谓 Ontology 建设，不过是在用 2026 年的技术名词，重复 2006 年的需求调研方法。

## 用几个简单问题评价一个国产 Palantir

不要看它有没有 Ontology Designer，也不要看它能不能画出漂亮的对象关系网络。更不用看演示现场那个 Agent 能不能回答“这个项目当前有什么风险”。

只需要问几个工程问题：

- 它的对象是围绕真实工作流逐步形成的，还是先做一套全企业概念模型？
- 对象背后的主键、数据源和血缘是否可以追溯？
- 不同系统数据冲突时，是简单清洗成一个值，还是保留来源并建立可裁决机制？
- 用户能不能直接针对对象执行 Action，而不是跳回原业务系统？
- Action 有没有权限、校验、事务和审计？
- 执行以后能不能写回真正的生产系统？
- 这些业务动作和人的决策能不能继续成为下一轮计算的数据？
- 最后，同一个行业的第二家客户进来时，到底有多少东西可以直接复用，而不是重新派一批咨询顾问驻场半年？

如果这些问题大部分答不上来，但厂商可以给你展示一个非常复杂的企业 Ontology 图，那么你看到的大概率不是 Palantir。你看到的是一个知识图谱。如果它还能接几十套数据库，那是一个数据中台。如果上面再接一个大模型，那是一个 AI 数据中台。如果项目需要几十个人长期驻场，不断调研、映射、改模型、维护接口，那么它的商业模式最终还是那个我们已经非常熟悉的东西：**项目外包。**

## 真正难的是如何把软件重新变成业务本身

Palantir 最容易模仿的是产品外观。Object、Link、Ontology Manager、地图、关系网络、低代码应用、AI Agent，这些中国软件公司完全能够做出来。真正难复制的是它背后的一个工程判断：数据平台不应该永远停留在业务系统旁边观察业务，而应该逐渐进入业务运行本身。

当用户发现一台变压器风险过高，他不应该只在数据平台上“看到风险”，然后打电话、发微信、登录另一套系统开工单。他应该能够在同一个受权限控制的工作流中完成判断、执行动作、留下原因，动作再安全地进入真正的业务系统。到了这一刻，Ontology 才不再只是对企业的描述。它开始成为企业运行的一部分。

而国内绝大多数所谓“对标 Palantir”的方案，恰恰停在前一步：不断努力让系统**更完整地描述企业**，却始终不敢、不能或者根本没有能力让它**真正参与企业运行**。

所以问题从来不是中国有没有自己的 Ontology 技术。对象建模并不神秘，知识图谱也不是新东西。真正的问题是：我们到底想做一个新的数据项目，还是准备改变企业软件的组织方式？

如果答案依然是立项、调研、梳理、建模、集成、验收，然后留下一支运维团队继续维护接口和映射关系，那么无论方案里写多少次 Ontology、AIP、Agent 和数字孪生，都没有关系。它还是数据中台，只是这一次，数据中台终于学会了说：**Palantir。**
