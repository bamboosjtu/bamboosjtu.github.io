# 为什么企业 Agent 最后都会撞上旧系统：从浏览器操作、API、MCP 到权限审计

最近在研究企业 Agent 时，我遇到过一个很现实的问题。我希望 Agent 能够操作公司已经运行多年的业务系统。和负责系统技术支撑的同事讨论以后，对方给出的方案很符合传统信息化建设思路：**需要改造原系统，增加 MCP 接口。**

从长期架构上说，这当然不能算错。但真正开始往下想以后，我发现这里至少还有三个问题没有解决。

- 第一，改造原系统意味着需求、设计、立项、开发、测试、上线。在大型企业里，这套流程几乎天然以月为单位。一个原本只是想验证“Agent 能不能完成这项工作”的问题，很快就会变成一个标准的信息化建设项目。

- 第二，更麻烦的问题其实是：**MCP 到底应该怎么设计？** 是把现有几百个 HTTP API 原样变成几百个 MCP Tool，还是重新按照业务语义抽象成 `project.search`、`project.get`、`project.list_risks`、`workflow.submit`、`document.export` 这样的能力？如果是后者，那么谁来定义这些能力——原系统开发商、业务部门，还是 Agent 平台？

- 第三，即使 MCP Server 建出来了，认证、用户身份继承、数据权限、写操作审批和审计仍然没有消失。Agent 到底代表谁？继承谁的权限？哪些动作可以自动执行？最后出了问题，责任算在人、Agent 还是系统？

于是我开始想另一个问题：**如果暂时不改原系统，Agent 能不能先使用它？**这个问题后来改变了我对企业 Agent 建设方式的理解。因为再往下走，会发现真正值得警惕的可能不是“旧系统不支持 MCP”，而是我们正在下意识地用建设传统数字化系统的方法建设 Agent。

## MCP-first，很可能只是传统系统集成披上了 AI 外衣

企业非常擅长把一种新技术吸收进既有建设模式。过去系统之间需要交换数据，于是建设 WebService 和 ESB；后来要服务化，于是改 REST API；再后来要数据汇聚，于是接数据中台。今天 Agent 需要调用工具，于是一个非常自然的答案又出现了：每套业务系统增加 MCP。技术名词一直在变化，但建设模式几乎没有变化：先做需求调研，再确认需求、立项、系统改造、接口建设、联调测试，最后上线。如果一家企业有一百套业务系统，那么很容易得到一个看起来非常完整的规划：一百套系统逐步完成 MCP 改造，最终形成企业级 Agent 工具体系。

问题是，这个逻辑有一个致命前提：**你必须事先知道 Agent 到底需要什么。** 而这恰恰是今天最难知道的事情。传统数字化建设通常围绕相对确定的流程展开。我要建设一个合同管理系统，可以先定义合同有哪些状态、有哪些审批节点、有哪些角色；我要建设一个项目管理模块，也可以提前梳理字段、表单和流程。但 Agent 不一样。Agent 的价值很大程度上来自它能够在已有系统、数据和工具之间重新组合工作，很多真正有价值的用法，不是需求调研阶段写出来的，而是在模型真正接触业务以后才被发现。

如果在 Agent 还没有实际使用系统之前，就要求业务人员一次性定义完整 MCP 需求，很容易进入一个非常典型的死亡螺旋：要设计 MCP，就需要先知道 Agent 会做什么；要知道 Agent 会做什么，就需要让 Agent 先使用系统；但系统还没有 MCP，于是 Agent 暂时不能使用；最后大家只能继续开会讨论 MCP 需求。讨论到最后，最容易得到的其实还是原系统开发商最熟悉的东西：现有接口清单。`/queryProjectList`、`/getProjectInfo`、`/getDictionary`、`/saveForm`、`/exportExcel` 被重新包装成 `query_project_list`、`get_project_info`、`get_dictionary`、`save_form`、`export_excel`。技术上当然可以运行，但这并不是 Agent Capability，只是旧 API 换了一件 MCP 外套。**如果 MCP Tool 的定义主要来自 Swagger，而不是来自 Agent 的真实工作，那么这个 MCP 项目从第一天开始就很可能走偏了。**这也是我认为企业 Agent 和传统数字化开发最需要拉开距离的地方。不是说智能化项目不需要需求管理，而是不能再假设所有有价值的需求都能在开发之前被完整定义。如果还坚持“先冻结需求，再立项开发，最后交付 Agent 使用”，那么我们做出来的很可能仍然只是数字化，只不过 UI 上多了一个聊天框。

## 与其先改系统，不如先让 Agent 用起来

如果不把“原系统必须支持 MCP”作为前提，事情马上会简单很多。一个旧系统可能没有开放 API，没有 SDK，没有 MCP Server，但它只要仍然有人使用，就至少还有一个接口：浏览器。所以 Browser Use、Playwright、web-access 这一类方案真正有价值的地方，并不只是“AI 可以点网页”，而是它们打破了一个隐含前提：**目标系统不需要先为 Agent 做准备。** 人能够登录，Agent 就有机会登录；人能够选项目、点菜单、下载文件，Agent 就存在一种自动化路径。浏览器因此成了旧系统最后的兼容协议。当然，浏览器只适合打开第一扇门。如果一张表有两万条数据，每页二十条，让 Agent 点一千次“下一页”显然不是智能化，只是在用昂贵模型模拟一个非常低效的人。真正进入系统以后，更合理的方式通常是观察页面背后的网络调用，然后逐渐把确定性操作转到 API。

于是很自然地会形成一种混合模式：浏览器负责 SSO、MFA、登录、建立 Session 和选择业务上下文，API 负责结构化查询和确定性操作。浏览器解决“怎么进入真实业务环境”，API 解决“进入以后怎么稳定执行”。这类方案一点都不“优雅”，但它解决了一个非常重要的问题：**可以在几乎不修改原系统的情况下，让 Agent 先进入真实业务。**而且这里也不一定需要一开始就建设完整的企业身份平台。在探索阶段，现有用户凭据本身就是最朴素的身份来源。把账号凭据放在 `.env` 或运行环境变量中，由 Skill 在需要时读取，用用户本来的账号登录系统，权限继续由原系统控制，这已经是一套可以工作的最小 Identity 实现。

它当然不是企业级 IAM 的终局，也不适合直接支撑大规模无人值守写操作，但这并不妨碍它作为探索阶段的实现。**PoC 最大的错误之一，就是要求第一天就具备生产系统最后一天才需要的完整治理能力。** 先解决“能不能做”，再解决“应该允许做到什么程度”，这两件事应该分开。

## Skill 的价值，是让需求从真实使用里长出来

把旧系统通过 Browser 和 API 接通以后，下一个问题是：到底应该向 Agent 暴露什么？

这时 Skill 的价值就开始明显起来。我后来更倾向于在现有系统之外先包一层 Skill，而不是让模型直接面对一堆接口。Skill 下面可以是 Browser，可以是 detach API，可以是本地 CLI，也可以是几个完全不同的系统。底层实际发生的事情可能很复杂：打开页面、选择业务对象、获取 Session、调用接口 A 和接口 B、合并结果。但 Agent 不应该每次都重新理解这套技术细节，它应该逐渐看到 `project.search`、`project.current`、`project.progress`、`plan.list`、`document.export` 这样的业务动作。

这里最关键的一点是：**这些 Capability 不应该一开始就被当成固定需求设计出来，而应该从真实使用中逐渐抽象出来。**

这也是 `a-stock-data`、OpenCLI 以及各种浏览器 Skill 给我的最大启发。重要的不是它们分别使用了什么技术，而是它们暗示了一种完全不同的软件开发方法：先让 Agent 接触真实世界，再观察哪些动作值得固化。于是开发过程不再是“需求定义—接口设计—系统开发—用户使用”，而更像“探索—运行—观察—抽象—固化—再运行”。模型能力本身存在不确定性，用户如何使用 Agent 也存在不确定性，很多需求不是不存在，而是只能通过真实使用被发现。所以我更倾向于把 Skill 看成 Agent 时代的一个**低成本业务实验层**。它可以很薄，可以不漂亮，甚至可以先只是几个脚本和一份 `SKILL.md`。关键是让 Agent 真正进入工作，再从交互记录和业务反馈中发现：哪些动作反复出现，哪些参数总是一起出现，哪些底层 API 应该组合，哪些操作实际上没人使用，哪些流程模型自己能够组合，哪些地方必须增加确定性约束。到这一步以后，Capability 才真正开始有意义。

## Capability 应该从使用中长出来，MCP 是它成熟后的出口

我旗帜鲜明地反对“先设计一套完整企业 MCP Tool 体系”这种做法。并不是因为 MCP 不重要，而是因为它太容易把一个仍在探索的问题过早固化。假设后台有 500 个 API，真正跑了一段时间 Agent 后发现，80% 的任务实际只依赖十几个业务动作，例如 `project.search`、`project.get_progress`、`project.list_abnormal`、`workflow.pending`、`document.export`。那么这十几个才是真正值得长期治理的 Capability。这时再去问它的输入 Schema 是什么、输出应该标准化到什么程度、哪些字段属于稳定契约、哪些操作是只读、哪些有副作用、哪些需要审批、哪些应该成为 MCP Tool，这些问题才有真实依据。

所以我更认可这样的顺序：

```text
Browser / API
      ↓
   Skill
      ↓
真实业务使用
      ↓
Capability 抽象
      ↓
稳定性验证
      ↓
     MCP
```

MCP 在这里不是起点，而更像一种**毕业机制**。某个能力经过真实业务反复验证以后，才从探索性的 Skill 内部实现，升级为正式、稳定、受治理的企业 Capability，然后再通过 MCP 或其他协议标准化暴露。这和传统软件里从原型走向公共 API 没什么本质区别。区别只是今天很多企业跳过了前面所有阶段，直接从“我们要做 Agent”跳到了“请各系统报送 MCP 改造需求”。这是非常危险的。因为一旦走进传统立项流程，每一个 Tool 都开始需要需求确认、接口文档、开发工作量、测试验收。最后大家自然会倾向于“一次性把需求想清楚”。但 Agent 应用目前恰恰是最不适合一次性把需求想清楚的软件。于是一个很荒谬的局面出现了：**为了建设一个本应帮助企业处理不确定任务的智能系统，我们首先要求所有需求必须确定。** 这就是典型的用数字化方法建设智能化。最后非常容易得到一种结果：技术正确，业务无用。MCP Server 都上线了，Tool 也有几十个，架构图非常漂亮，但真正问业务人员“你每天让 Agent 做什么”，答案仍然不清楚。

## 权限和审计必须升级，但应该跟着能力成熟度走

当然，一旦 Agent 能够真正操作业务系统，Identity、Policy 和 Audit 最终一定绕不过去。但这里同样要避免另一个极端：一提企业 Agent，就马上要求设计完整的 OAuth Delegation、RBAC、ABAC、Policy Engine、审批流和全链路审计，然后因为基础设施还没有建设完成，结论变成“暂时不能做”。这同样是传统信息化思维。探索阶段完全可以使用更简单的模型，例如 `.env` 或环境变量加上用户现有账号，继续复用原系统认证和原系统权限，再配合只读优先、危险动作 fail-closed、显式允许写操作、本地日志等简单措施。这至少保证了 Agent 没有凭空获得新的业务权限，也足够验证大量低风险场景。

真正的问题应该随着能力成熟逐步升级。当 Capability 从“个人辅助工具”进入“多人共享工具”，Identity 就需要从 `.env` 升级成统一身份；当 Agent 开始自动写数据，Policy 就需要从简单 allowlist 升级为细粒度授权；当 Agent 可以提交审批和改变关键业务状态，Audit 就必须能够回答完整的责任链：是谁提出了请求，Agent 做了什么判断，调用了哪个 Capability，使用了什么身份，权限系统为什么放行，以及最终改变了哪些业务数据。所以权限治理不是不重要，恰恰相反，它非常重要。只是正确顺序不应该是“先把所有治理基础设施建设完成，Agent 才能开始工作”，而应该是：**能力跑到什么风险等级，治理就升级到什么等级。**

## AI 开发真正应该打破的，是“先定义完需求再开始”的幻觉

回过头来看，我现在认为企业 Agent 对传统信息化最大的挑战，可能根本不是技术栈，而是开发方法。传统数字化系统倾向于先问“需求是什么”，然后把需求冻结下来，再据此设计系统。Agent 项目更应该先问：**我们能不能让模型进入真实工作，然后看看什么值得被产品化？**这并不是不要架构，更不是不要治理，而是把架构建设顺序反过来。先追求可达性，再追求可用性，然后再做标准化，最后才进入规模化治理。换句话说，路线更像：

```text
旧系统
  ↓
Browser / API
  ↓
Skill
  ↓
真实使用
  ↓
Capability
  ↓
MCP
  ↓
Identity / Policy / Audit
```

这条路线和传统“需求—立项—开发—交付”最大的区别，是允许需求在运行中出现，允许接口在使用中收敛，也允许错误的 Capability 被快速丢弃。Agent 技术真正改变软件开发的地方，也许就在这里。过去我们先定义系统，再让人适应系统；现在完全可能先让 Agent 适应现有世界，再从真实行为中反向定义新的系统边界。所以企业 Agent 最后都会撞上旧系统，并不是因为旧系统阻碍了智能化。恰恰相反，旧系统迫使我们回答一个更重要的问题：**我们到底是在用 AI 改变软件开发方式，还是只是把 AI 塞回传统信息化建设流程？**

如果答案仍然是先立项、先冻结需求、先要求所有系统改 MCP，再等待 Agent 接入，那么所谓智能化最终很可能只是又一次系统集成。而我更愿意相信另一条路：**先接进去，先跑起来，先产生真实反馈，然后再抽象、标准化、治理。**MCP 当然会出现，Identity、Policy、Audit 也一定会出现，但它们应该建立在已经被真实业务证明有价值的 Capability 之上，而不是建立在我们对未来需求的想象之上。否则，我们最终得到的很可能是一套非常标准、非常安全、非常完整，却没有人真正需要的企业 Agent 基础设施。
